# What an agent can do on the harness engine

On the harness engine nothing in LumiRPEngine plays a turn: the author and the agents it starts decide everything by calling tools, and the engine checks and records what they call for. This page lists every surface a game master can read or change in LumiRPEngine (the GM pages and the requests behind them, the change types, the packs) and says what an agent can do to it through a tool. Where a surface is not an agent's to change, the table says so and why.

A test holds this page to the engine (`test/backend/harness-cast-docs.test.ts`). It fails when a tool named here doesn't exist, when a tool the harness lists is missing from the table, when a surface can be created on but not read, when a tier here is not the one the engine's registry gives the tool (`HARNESS_LISTED`, its `needs`), and when the bridge lets a call through that the tier closes: in a real turn it calls every listed tool as an agent that only reads, as one at the story's tier and as the author, and expects each call refused or let through as the tier says, before the tool runs. It also calls every tool once with no arguments, which proves only that each answers in words and reaches no model. What a tool does is proven in its family's own tests (`test/backend/harness-cast-*.test.ts`).

Another test holds each agent to the tools its texts name (`test/backend/harness-cast-held.test.ts`). Every tool named, as a whole word, in an agent's instructions, in what a chat adds to them (its part of the preset, the narration lines, the author's opening), in the world's guidance and in each skill it is offered must be one its definition gives it in a chat the engine plays. A word written like a tool's name that names none fails, and so does a text that tells an agent to start one (`delegate` or `job_start` with its id) that doesn't exist or that it can't start. Each skill is offered only to the agents that hold every tool it names. Every tool listed here is held by at least one agent, or is named in that test with why it is nobody's. When a turn starts, an agent of the engine's that can't use a tool it is given there (switched off on the Tools page of the Harness tab, or not there) keeps the turn from starting, in words that name the agent, the tools and what to do.

## How to read it

- **Surface**: what is read or changed, with the page or request a game master reaches it by.
- **Tool**: the tool's name. A tool that serves several surfaces is listed under each.
- **Does**: `create`, `read`, `change`, `remove`, one or several.
- **Tier**: who may call it.

| Tier | Who may call it |
|---|---|
| `read` | Any agent given the tool. It changes nothing. |
| `story` | An agent at the story's tier or above: a change the story itself makes (the historian holds this tier, and so does the author). |
| `gm` | An agent at the game master's tier: the author, or an agent the author granted it to (`grant_writes`). |
| `author` | The author alone, in its own turn: the run's main agent, never an agent it started and never an agent of a job. |
| `mind` | A character's own agent alone, for the one person it is. |
| `any` | Any agent given the tool: what it records is checked by the engine's own validator for the step it stands in for, and the tool itself holds who may do what with it, by the definition the caller runs as and the person it runs as. |

Whatever tools an agent's definition lists, the bridge holds every call to the tool's tier before the tool runs, and no agent writes above the one that started it: started by an agent that only reads, an agent only reads, in a turn and in a job. A grant (`grant_writes`) raises an agent to the story's tier or the game master's for the rest of the turn, never above the author's own and never past the agent that started it; a character's agent takes none.

What an agent passes a tool is what a model said. Before any tool reads it, every string in a call's arguments has its macros' braces and its `<user>`-style shorthands broken and its control characters dropped; a string that is itself JSON is treated inside, value by value.

Every change is staged with the turn and lands when the author commits (`commit`), under the mode the player set for its change type (Settings → Changes from the reply): Auto lands, Confirm waits on the review card, Never is refused. After the reply, in a job's run, a change is written as it is made, under the same modes. Every tool that writes has a change type: one of the old engines' tools its own; what the author plays (`action_play` and the fight tools) "What the author plays"; a mind's own tools "Characters' minds"; the turn's time (`time_pass`) the type of time passing; the world's document its own (below). `time_pass` with 0 minutes records nothing, so no mode has anything to refuse: it only says that the turn takes no time. Three kinds of write are no event of the chat's record, so each says here how it holds to its mode: the world's draft (below); a file kept in the harness's workspace (a lore entry saved under `lore/` or drafted under `lore-drafts/`, under "Workspace notes": written at once under Auto, staged for the review card under Confirm, refused under Never); and a mind's file (`mind_write`: written under Auto, refused with the reason under Confirm, since a file can't wait on the card, and under Never).

The dice are the engine's. An attempt is read with `checks_stakes`, which answers the odds and what each outcome does and never a roll; the roll is made once, when the author plays the attempt (`action_play`, or `fight_round` inside a fight), and is recorded with what it did. It is drawn from the turn, who rolls and how many rolls the turn has recorded for them: no argument and no wording moves it, and an argument the action doesn't declare is refused.

The world has two places an agent writes it. This chat's own world is the default for a place of the world's own, a path between two places, a map and the map settings (`world_place`, `world_path`, `world_map`, `world_map_place`, `world_map_link`, `world_map_settings`, and `world_put`/`world_remove` for places, routes and maps): each write is one change of the type "The world as this chat plays it", staged with the turn under its mode like any other, played at once (the caller's next call sees it, everyone's once the author commits), recorded on the reply, and gone with its turn (a swipe, the whole turn undone). An Upgrade carries it to the new revision, as it carries what play wrote of people and things: a change the revision has as the chat made it (kept and committed) goes, and the world's own plays from then on; one the revision changed otherwise is kept, and plays on. `world_made` lists what this chat made or changed that the document lacks, and `world_keep` copies it into the world's draft. With `in: document` those tools, and every tool of the document's other collections and parts, write the world's draft as Build does: nobody plays it until it is committed and the chat brought to it. Each such write is for the draft as its tool just read it: one written to in between is refused. The four that change what was authored for every chat, or can throw work away (`world_commit`, `world_upgrade`, `world_discard`, `world_restore`), go through the same gate as every other change, under the change type "The world's document": staged with the turn and decided when the author commits, by the mode set then. As shipped it lands when the author commits (an Upgrade made inside a turn lands at the turn's end), and the reply lists each commit with **Open in Build**; undoing the turn leaves the world's document as it is. Whatever the mode, a commit, a drop or a restore of a draft that holds edits no agent of the turn wrote (the user's own unfinished work in Build) goes to the reply's review card with a line that says so: no agent publishes or throws away the user's work. A commit, an Upgrade and a restore say what they would change against the world's head, by collection; what the world keeps from the player's character is counted on the card and never named. Under Never every write of the document is refused, the draft's own edits too. What could never be applied is refused when asked: a draft with errors, a draft begun on an older head, and a revision the world doesn't have.

Some of the document is closed to agents, whatever the mode: who the player's character is, and what the engine limits or checks agents by. No draft tool writes one of these paths, by any route (a patch of it or of what holds it, a part set whole, a pack put whole), and no agent commits a draft that changes one, restores a revision that differs in one, or brings the chat to a revision that differs in one from the one it plays. Each such call is refused with the paths, and is the user's to do in Build. Everything else, the world's content and its rules, is an agent's to build.

| Closed path | Why |
|---|---|
| `/pov` | Who the player's character is. Every rule that asks it (whose mind no agent may be, whom a secret is kept from) is asked of this one value. |
| `/spawnCap`, `/placeCap`, `/placesPerTurn` | How many people and places a chat's replies may bring in. |
| `/packs/economy/config/claimCap`, `/packs/economy/config/unpricedCap` | The price past which a thing made for the story asks first, and the most a narrated price may be. |
| `/realism/claims` | What a reply may make real of what the player says they have. |
| `/narrator`, `/minds/secrecy` | What the narrator is told: whose knowledge, whether secrets, how much of a mind. |
| `/loreBooks` | Which of the user's own World Info books the world reads. |

A place of the world's own, a way between two places and a map written to this chat's own world (the default) are played from the call that made them, and undone with their turn. Written to the world's draft (`in: document`), they are played only once the draft is committed and the chat brought to it. A place made in play (`place_make`) is reached through the place it is under.

The story record (DEPTH2-PLAN §4) is the reply's record's own part (`Rec.story`): the beats a turn wrote and whom each reached, the beats it struck, each casting it set and each draft as it left it. It is outside every hash, so it follows swipes and branches with the record and moves nothing of the world. In a turn a change to it is staged with the turn and kept when the turn commits; in a job it is written on the record of the turn the job belongs to. Its tools hold who may call them themselves, by the definition the caller runs as, past the bridge's gate: `beat_write` the author and the game master for any beat, a character's agent only for its own acts, as the person it runs as; `feed_read` a character's agent, for that person; `cast_set` the author alone; every other the author and the game master. Every limit is the player's (`story.limits`, `story.budget` in the settings).

A passage of the reply (DEPTH2-PLAN §3.3) is the turn's own, in memory, until it goes out. Each passage is numbered 1, 2, 3 in the order told, and each narrator keeps to the number its task gives it, however many are at work: `narration_read` with a number past the next is refused, naming the next, and one that names none opens the next; `passage_draft` drafts only the passage the narrator's last `narration_read` gave it, revisions included, and a narrator reads only a passage seen through its own eyes. The narrator is handed what reached the point-of-view character that no earlier passage tells (`narration_read`: never more of a beat than reached them), going on from each earlier passage that passed its check (one not settled is named, never handed), and drafts it (`passage_draft`); a new passage with nothing left to tell is refused naming the passage that told the last of it, so its beats are recorded after that one; a draft made before its check takes the place of the last and spends none of the drafts allowed, unless beats no passage tells reached those eyes since the narrator read it, which are a further passage's. It then answers its author in a line, which passage and how long, never its text; whoever the settings name checks it against the beats whole (`passage_read`, `passage_check`): the game master as shipped, the author, or no one. `passage_read` without a number lists where each passage stands, its figures and no text, so the author knows when to release without reading any passage. The author releases the reply once, whole, with LumiAH's `reply_write` as the engine gives it here: it names each passage by its number, in order (`pieces`), with any words of its own before or after them (`words`, `place`). The engine answers with the text that goes out: only the author releases, and where each passage is checked only a passage whose latest draft passed, or was checked with its drafts spent, goes out, with a few words of the author's own (`narration` in the settings); each latest draft in the order named, a blank line between them. LumiAH refuses a second release in the same turn. Where the author's run ends with nothing released (it answered, or a limit or a failure stopped it; never the player's Stop), LumiAH asks the engine for what its agents had ready (`unreleased`): the whole telling, only where every passage is settled and every beat that reached the player's character is told, marked as out only once LumiAH says it went (`released` with no arguments); otherwise nothing, and the turn fails as before. A narrator sees through the eyes the author named when it started it, the player character's otherwise.

The prepared start (DEPTH2-PLAN §1.11) is a job the player starts on Play → Now: the author's own run, which keeps its plan and progress in `author/prepare.md` and carries on from that file after a pause, a cancel or the player's word on its plan. The author surveys what there is (`prepare_survey`), plans before it spends (`prepare_plan`), and opens stretches of the chat for the historian (`prepare_relive`), who reads each (`stretch_read`, within Settings → Story → Preparing → One read of a stretch, its framing included; a message is never cut, and one longer than a read is given whole) and records it as beats marked as recorded from the past (`stretch_beats`, `Beat.past`); each principal the beats reached then relives them through its feed. The survey answers within Settings → Story → Preparing → One answer of the survey. Both sizes are listed to LumiAH as what the tool gives whole (`wholeChars`, as `mind_read` lists every mind file full), so a read or an answer reaches its agent in one piece rather than clipped at LumiAH's Tool results clipped past: fewer rounds, each a larger part of every later prompt (60,000 characters each as shipped; a stretch of forty 7,000-character messages takes five reads). Without a part, the survey gives what there is in outline; its summaries part, the story so far in the summaries' own text (read from the books' entries, a switched-off one too), the highest level first and the lower levels newest first, with what was left out for size by id and how to read it (by id, or a level in the story's order from a message on); its lore part, each book with its size and how many entries are always on, and a book's entries. On a chat with a history the plan is refused until the summaries and the lore were read in the preparation (the survey notes each part as given in `author/prepare.md`, so a later run need not read them again), and until the author has written the story as it understands it in `author/story.md`: what it is about for the player's character and the bigger picture the lore gives, what happened in order, and who the main characters are, with what each knows and wants now. The author adds to it after each part it reads, every later run reads it first, and a run whose prompt has no room left writes what it has there and ends; the player reads it in Harness → Notebook and corrects it by telling the author. The plan is reckoned in all, the author's own work included: what the preparation has spent, as LumiAH counts it, and the model calls it still takes at what one of its calls weighs (its own latest, the mean of its calls, this chat's last author run, or else Settings → Story → Preparing's figure for a call not yet measured). Each plan is reckoned at up to three depths, which the player picks between as they approve it, beside the author's recommendation and why: outlines only (every principal knows the past in outline, from summaries and lore, and nothing is relived), key moments (those outlines and the stretches the author marked `key`, offered only where some stretch is one), and everything planned; a stretch outside the depth chosen stays in the plan, not chosen, and is never opened, going deeper later carries the preparation on with the stretches it adds, and going shallower never undoes what was recorded. What the player tells the author always acts: told at once to a run under way, kept for a held one and told it on resume, else a run starts that revises the plan; a finished or cancelled preparation is opened again so. Their words never approve the plan: it goes back to waiting for their word whatever their ceiling, `prepare_relive`, `prepare_outline` and `prepare_finish` refuse until the plan is written again with the author's `answer` to them, and the card shows that answer under their words. The tools hold what matters: nothing is relived while the plan waits for the player's word (a plan reckoned above their ceiling on the whole, Settings → Story → Preparing, or revised for what they said), or once what it has spent and the next stretch's reckoning would pass their cap on all it may spend; stretches are relived in the chat's order; no more principals have reliving outstanding at once than the player allows; and the preparation closes (`prepare_finish`) only once it holds what a first turn needs. A preparation changes nothing in the world: in its job a change of the world is refused, and the author notes in `author/scene.md` what the first turn should set right.

Those whole reads pile up in the agent's prompt over a run, and nothing compacts inside a run, so the author and the historian ship with a Prompt per call of 160,000 tokens (`READER_PROMPT_TOKENS` in `backend/harness/definitions`): a 200,000-token window less the author's 32,000-token answer room and a margin. It is the user's, under Harness → Agents, and a version of the agent the user saves keeps its own limit (the engine owns only its name, description, instructions and tools). Set it about 40,000 tokens under what the model reads. At the limit LumiAH cuts a read to the room left and tells the agent so, and the agent writes what it has to its files and ends its run. The other agents stay unlimited: none of their reads grows without bound in one run, each held to its rounds and each read to its own size, which LumiAH gives whole (`wholeChars`). A read whose size is worked out from the limits of what it holds never states more than one ceiling (`WHOLE_READ_MOST` in `harness-tools/kit.ts`, 120,000 characters, about 30,000 tokens: whole for anything a writer may write in a turn, too small for one read to take an agent's window): `mind_read` to the mind's file sizes; `mind_seed` to the ceiling, the mind's files first and then the person's record, which nothing bounds; `feed_read` and `beats_read` to their counts of beats (Settings → Story → The record's limits), each beat as long as those limits let one be with every text counted as JSON may escape it, and the oldest (`feed_read`) or newest (`beats_read`) that fit within the size, the rest read on with `after` or `before`, which each answer gives before its beats; `narration_read` and `passage_read` to the longest passage Settings → Story → Narration allows with every change its checks may ask, the beats of a turn at the record's limits and every presentation module one call may name (the story preset's limits), each text counted as JSON may escape it; the lore reads, on the harness alone (in a turn or a conversation tied to none), to a page of `agents.clipChars`, read on by a cursor that notices an entry or a list changed since the page before. The prepared start's two reads are not held to the ceiling: `prepare_survey` and `stretch_read` state the player's own sizes (Settings → Story → Preparing → One answer of the survey and One read of a stretch, up to 1,000,000 characters), which a player sets high on purpose for a model with a very long context. Every other read is held to LumiAH's Tool results clipped past.

Each run of the preparation is a job of LumiAH's started with the run's own allowance (Settings → Story → Preparing → Time for one run and Rounds for one run, never LumiAH's allowance for any job; no token limit of its own, the player's cap holding what the whole spends), and told, in place of LumiAH's own ask that a job write its plan, that the preparing tools keep `author/prepare.md`, the plan of the whole preparation, and that the allowance bounds that run only (`backend/story/prepare-run.ts`). When a run ends with the preparation unfinished, the engine starts the next by itself (`backend/story/prepare-carry.ts`) while the plan has the player's word as it stands, nothing in it waits for their word, they didn't hold or cancel the run, and their cap leaves room for another call. It doesn't after a failure a new run would only meet again (LumiAH marks such a job lasting: no connection to run on, a key or a model refused), a day's limit or a run cut off, nor once as many runs it started in a row as Runs without progress moved the preparation nothing forward by the file's own account of what is left. Each end is logged in the file, carried or stopped with why, and the card says why it stopped, with Carry on. What each run spent is written into the file by job as it ends, so what the whole preparation has spent, and the cap held to it, counts every run, however many have fallen out of the jobs LumiAH lists.

While it runs, the card on Play → Now shows it live (`lre.prepareLive`, `backend/story/prepare-live.ts`): a line and a bar that open into the whole, kept open or closed for the chat. The whole says where it stands (reading the story, planning, waiting for the player's word, reliving, filling in the rest, setting the scene, ready), who is at work (the author's runs, the historian on the stretch it records inside them, each principal's reliving run on its stretch, and the last run of anyone's that stopped before its work was done, with LumiAH's reason and what can be done), how far each stretch and principal has come (whom a recorded stretch reached and who is through it, as the file last worked it out; the stretches the chosen depth leaves out), the chat's messages relived, filled from summaries and neither, when it started and how long its runs worked, what it spent against its reckoning and the cap, a rough time left once a stretch is done, and a trail of what happened, newest first. It reads only what is cheap to read, so it can be asked every few seconds for hours: the preparation's file (its log, the chat as the plan found it, whom each stretch reached), one page of the chat's jobs and the list of the chat's files; never the chat's messages, its World Info or the story record. It asks again every Settings → Story → Preparing → **The live view asks every** seconds while a run of it is at work, and stops once none is; **Runs the live view looks through** sets how many of the chat's latest runs it reads. A file written before a fact was kept says so in place of it.
